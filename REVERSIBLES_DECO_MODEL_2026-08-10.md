# Reversibles — decoration on 4 faces of one garment (2026-08-10)

Triggered by NSA Deco (Dylan Aasness), 2026-08-07, on SO-1469 (Esperanza Basketball,
Alleson 506CR reversible jersey, Cardinal/White): *"What is the color way for the
reverse (White) side of these jerseys? Everything I can see is only for the cardinal
side."* Steve's framing: jobs with reversibles only populate one side; reversible
garments often carry decoration on **4 faces** (front outer, back outer, front inner,
back inner).

## How the portal models a reversible today

A reversible is NOT modeled as four decoration locations. It's modeled as:

- `reversible` boolean per decoration row (`so_item_decorations` /
  `estimate_item_decorations`) — same position, billed ×2
  (`d.reversible?2:1` throughout pricing).
- Two ink colorways per art decoration: `color_way_id` (Side A) + `color_way_id_b`
  (Side B), both pointing into the art file's `color_ways` array
  (`so_art_files.color_ways`: `{id, garment_color, inks[]}`).
- Two mockup slots per reversible decoration, generated by `mockSlotKeys`
  (`src/safeHelpers.js:575`) — the declared single source of truth:
  - art Side A → base `sku|color` key; art Side B → `|<color_way_id_b>`,
    positional fallback `|d<i>_1`
  - numbers/names Side B → `|numbers_b` / `|names_b`
- Numbers/names print colors: `print_color` + `print_color_b`.

So the intended model per reversible garment is 2 positions × 2 sides = the 4 faces,
each with its own colorway + mockup. The schema and upload paths support it —
SO-1469 actually has all four mockups uploaded and correctly slotted
(`506CR|Cardinal/White (ba)`, `…|d0_1`, `…|numbers`, `…|numbers_b`).

## Root cause of "only one side populates"

The production/floor job view (`prodJobModal`) and the shared Production Job Sheet
PDF builder both select images via `_prodJobItemMocks` (`src/App.js:948`), which had
**drifted from the `mockSlotKeys` contract**:

1. The art-deco loop only read the Side-A slot key; the Side-B key
   (`|<color_way_id_b>` / `|d<i>_1`) was never read. Front-White mock dropped.
2. The numbers/names sweep used regex `/\|(numbers|names)(_\d+)?$/`, which does not
   match the `_b` suffix. Back-White numbers mock dropped.
3. The Decoration Spec row resolved only `color_way_id` — the Side-B colorway
   (`color_way_id_b`) was never displayed, and the CW chip read `name||label` while
   colorways store `garment_color`, so even Side A often showed "CW: —".

Net: the decorator saw exactly the two cardinal images and no white-side info — the
reported symptom. This is the hand-synced-duplicate-logic failure mode
`FABLE_SYSTEM_AUDIT_2026-07-03.md` warns about: `mockSlotKeys` writes the keys, a
separately-maintained reader in App.js silently reads a subset.

## Fixed in this change (`src/App.js`)

- `_prodJobItemMocks`: reversible art decos now also push the Side-B slot
  (`color_way_id_b` → fallback `d<i>_1`); `_isNN` and the numbers-first ranking
  accept the `_b` suffix. This fixes both the on-screen floor job card and the
  printed/downloaded job sheet (both call `collectItemMocks` →
  `_prodJobItemMocks`).
- Floor Decoration Spec: resolves and renders the Side-B colorway — "CW A / CW B"
  chips plus a "Side B:" ink-swatch row; colorway labels fall back to
  `garment_color`.

Verified: `src/__tests__/mockSlots.test.js` (the slot-key contract suite) passes.

## Still open — data/workflow gaps on SO-1469 itself

The code fix makes side-B **mockups** show, but on SO-1469 the structured ink data
was never entered: the jersey's art file ("Reversible Chest Logo") has
`color_ways: []` and the deco's `color_way_id` / `color_way_id_b` are both null. So
its spec line still shows no inks for either side — the white-side answer currently
lives only in the mockup images (white body: cardinal text, gold number). The rep
needs to define the two colorways on the art file and pick them on the deco. Worth
considering: the art-approval gate already enforces "all four slots mocked" for
reversibles (`skusMissingMockups`); it does not enforce colorways A/B being set.

## Bigger-picture options (not done — needs a decision)

The 2-position × 2-colorway model covers the common reversible case, but it assumes
the inner faces carry the SAME art/position as the outer faces, differing only in
ink colors. Cases it cannot express: different art inside vs outside, an
inside-only location, or side-specific art sizes. If those come up for real orders,
the options are:

1. **Stay on the A/B model, harden it** (recommended, cheap): enforce colorway A/B
   entry when `reversible` is set; label mockup captions "Side A/Side B" on every
   surface; audit remaining display surfaces (coach approval view, work-order
   sheets `src/lib/workOrderSheet.js` renders only 2 mockup panels) against
   `mockSlotKeys`.
2. **Add a side axis to decorations**: a `side: outer|inner` column alongside
   `position`, one decoration row per physical face. First-class 4-face support,
   but touches pricing (the ×2 multiplier), every spec renderer, and both
   estimate/SO decoration tables — a migration plus UI redesign. Only worth it if
   reversibles with genuinely different inner/outer art become common.
