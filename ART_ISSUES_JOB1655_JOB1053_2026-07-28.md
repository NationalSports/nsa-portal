1. **SO-1655 (OLu Water Polo):** *"mockups were sent back to me for JOB-1655-03 and I submitted

2. **JOB-1053-02 (SF Volleyball):** *"This job keeps showing up on in my NEEDS APPROVAL column.
   Not sure why this is attached to this job. SO-1053 is for OLu Flag, and there's no artwork on

## 1. Executive summary

**Neither job lost any data.** Both `so_jobs` rows were intact in the database throughout, and no
save was lost. These are two different visibility defects:

- **JOB-1655-03 never left the approval queue.** Jered's "adjustment" was saved as a **chat
  comment** ("The background of the shield should be vegas Gold.", 8:55 AM), not as a revision
  request — the job's status never changed from `waiting_approval` and no rejection was recorded,
  so **nothing went back to the artist**. What "disappeared" is the dashboard to-do card: clicking
  a "Mockup ready for review" to-do **snoozes it for 1 day on every dashboard surface**
  (`_todoClickedThrough`, App.js), so after he clicked in, commented, and came back, the card was
  gone with no visible way to reach the job again. The job is still fully accessible — Art page →
  Needs Approval column, and SO-1655 → Jobs tab. **Action needed: someone must actually submit the
  revision** (Request Revision on the job) or Erik will never see the vegas-gold change. CONFIRMED
  (mechanism of the comment-not-revision save and the unchanged status; the snooze as the specific
  thing he saw is inference — it's client-local state, not in the DB).

- **JOB-1053-02 was an immortal ghost.** SO-1053 (OLu Flag) has carried a stray March "SF
  Volleyball" embroidery art file since before audit retention. On 7/23 an auto job was generated
  from a decoration wired to it; on 7/23–7/24 Jered removed that decoration and deleted the art
  file — but the job row survived, because the empty-jobs wipe guard in `dbEngine.js` **protects
  any job with `art_status !== 'needs_art'` from deletion** and there is no rep-facing way to
  override it. Every open of SO-1053 recomputed `jobs: []`, hit the guard, and was blocked; the
  ghost kept rendering in the Art board's Needs Approval column (that column reads `so_jobs`
  directly and ignores to-do dismissals — Jered had in fact dismissed the to-do twice, both
  recorded in `dismissed_todos`). CONFIRMED. **Fixed both ways** (§4): the row is deleted, and the
  guard now retires provably-dead jobs.

(`type:'art'`). Clicking it to review calls `_todoClickedThrough` → `snoozeTodoUntil(t,1)` — hidden

The card returns tomorrow — but the deeper problem is that **his colorway note went into the art
chat, not into a Request Revision**, so from the system's point of view the rep is still the one
holding the ball.

**Operational action (time-critical):** open SO-1655 → Jobs tab → JOB-1655-03 → Request Revision
with the vegas-gold note (or approve/reject through the mockup view). Until that happens, Erik's

**Recommended product follow-ups (not done in this change — they're behavior decisions):**
1. When a rep posts a chat message on a `waiting_approval` job, prompt: "Send this back to the
   artist as a revision request?" — the comment-instead-of-revision path is exactly how this
   request went nowhere.
2. Reconsider the click-through snooze for `type:'art'` to-dos — hiding an approval card for a day
   because it was *opened* (not actioned) reads as data loss to reps. The code comment already
   acknowledges a real state change should be what clears it.

## 3. JOB-1053-02 — the immortal ghost

- SO-1053 (Orange Lutheran Flag Football, "2026 AdiCustom Uniforms", created 5/20) is a normal
  order — **no order-ID collision** (created_at/customer stable across its whole audit trail).
- Art file `af1773688228325` ("SF Volleyball", embroidery, created ~3/16 — **two months before
  SO-1053 existed**) sat under `so_id='SO-1053'` with status `approved`. Its INSERT predates audit
  retention, so how it arrived can't be proven; the shape matches the known recycled-number /
  carried-over-art class (see the SO-1057 note in `dbEngine.js`).
- A decoration wired to it existed on the order's items until **7/23 18:20**, when Jered removed
  it. The auto job JOB-1053-02 had been generated at 18:07 that day (`waiting_approval`, 25u).
- **7/24 13:59** Jered deleted the art file itself. From then on the job referenced an art file
  that no longer exists, on an order with zero decorations.
- Every subsequent open of SO-1053 made `syncJobs` retire it → save `jobs: []` → the wipe guard
  (`dbEngine.js`, SO-1487 fix) **blocked the delete** because `art_status='waiting_approval'`, and
  only `so._deleteJobIds` (the admin Delete Job button) can override — nothing rep-facing.
- The Art board's Needs Approval column is driven straight from `so_jobs.art_status`
  (`getArtFileStatus`, App.js) — to-do dismissals don't apply there. Jered dismissed both related
  to-dos (`art:SO-1053:JOB-1053-02`, `items_received_needs_art:SO-1053:JOB-1053-02` — both in
  `dismissed_todos`) and the card still rendered. Hence "keeps showing up." CONFIRMED end to end.

### Repairs applied

1. **Production data (2026-07-28):** deleted `so_jobs` row `JOB-1053-02` on SO-1053. It carried
   nothing irreplaceable — `_auto: true`, no art requests, no rejections, no coach state, no
   artist; full row content is preserved in `audit_log`. A production-wide sweep for other jobs of
   the same class (protected status + dead art pointer + zero decorations on the SO) returned
   **only this row**; nothing else needed repair.
2. **Code (this change):** the wipe guard now runs a **DB-side liveness check** before blocking.
   A protected job is retired only when the *database itself* (never the client payload — a
   stale/short-loaded tab is what the guard exists for) shows **zero decorations on the SO's
   items AND none of the job's declared art files still exists on the SO**. Jobs with no declared
   art (numbers/names-only) stay protected; any read error keeps the protection. Live released
   jobs — art file present, or any decoration present — are blocked exactly as before.

**Tests:** `src/__tests__/deadJobRetirement.test.js` — 6 cases driving the real `_dbSaveSOInner`
through a mocked Supabase client. The no-false-positive cases are the load-bearing ones (art file
still exists / SO still has decorations / no declared art / liveness read error → still blocked).
